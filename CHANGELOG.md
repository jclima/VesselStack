## Version renumbering (2026-10-25)

The project is not ready for 1.0, so the version history was renumbered from 1.x to 0.x on 2026-10-25. Only the version numbers changed: the code, dates and behaviour of each release are as described in its entry. Former `v1.x` tags and GitHub releases were removed; use the `v0.x` ones. Mapping:

| Former version | New version | Date |
| --- | --- | --- |
| 1.4.1 | 0.4.1 | 2026-10-25 |
| 1.4.0 | 0.4.0 | 2026-10-24 |
| 1.3.0 | 0.3.0 | 2026-08-28 |
| 1.2.0 | 0.2.0 | 2026-08-25 |
| 1.1.0 | 0.1.0 | 2026-08-25 |
| 1.0.1 | 0.0.2 | 2026-08-21 |
| 1.0.0 | 0.0.1 | 2026-08-21 |

Note that the number 0.1.0 now means the former 1.1.0; an older, pre-release "0.1" configuration layout (migrated by the former 1.0.0 release) is a different thing.

Upgrading a machine that installed a former 1.x release: its `config/installed-version` still says `1.x.y`, which is numerically newer than `0.4.1`. `migrate.sh` and `get-vesselstack.sh` contain a one-time renumbering shim that treats an installed 1.0.0/1.0.1 as 0.0.1/0.0.2 and any other installed `1.M.P` as `0.M.P` when the target is a 0.x release, so `get-vesselstack.sh` or `vesselstackctl update` upgrade such machines normally (a 1.4.1 install is the same release as 0.4.1 and the marker is simply rewritten). Without the shim (an old `migrate.sh` from an earlier release) the upgrade is refused as a downgrade; the manual path is `sudo vesselstackctl backup`, then write the matching new number into `/opt/vesselstack/config/installed-version` (for example `echo 0.4.1 | sudo tee ...` for a 1.4.1 install; the configuration format of each release is unchanged by the renumbering), or reinstall 0.4.1 and `vesselstackctl restore` the backup.

## 0.4.3 - 2026-10-26

- Fixed: `SIGNALK_MODE=docker` first installs failed with `EACCES: permission denied, open '/home/node/.signalk/package.json'` and the SignalK container restarting. `VESSELSTACK_DATA` is root-owned since the data-root hardening and no release created `<data>/signalk` in docker mode, so Docker created the bind-mount source as `root:root`, which the image's `node` user (uid/gid 1000, config directory `/home/node/.signalk`, verified against `cr.signalk.io/signalk/signalk-server:v2.27.0`) could not write. `install.sh` now creates it as `1000:1000` mode 0750 before `compose up`, through the same symlink and ownership checks as the other managed mount roots. Native mode is unchanged (service-user-owned, created by `scripts/install-signalk-native.sh`); existing mode creates nothing.
- Fixed: upgrades repair an existing root-owned (or otherwise wrongly owned) `<data>/signalk`: chowned to 1000:1000 non-recursively when empty, recursively (never through symlinks, same filesystem only) otherwise, and the installer prints what it changed. A symlink at the directory or anywhere inside it is refused without changing anything.
- Added: `vesselstackctl doctor` checks the SignalK data directory in docker mode; when the container is not running and the directory is not writable by uid 1000 it fails with the symptom and the one-line fix (`sudo chown -R 1000:1000 <data>/signalk && docker restart vesselstack-signalk`), and only warns when the container runs.
- Audit: the other bind mounts need no change. Home Assistant and Heimdall write `/config` as root-started containers (Heimdall's linuxserver init chowns it to `PUID:PGID`; image behaviour read from the image documentation, not re-verified here, and both were healthy on a real 0.4.2 install); Mosquitto's entrypoint chowns `/mosquitto/data` to uid 1883 when started as root; InfluxDB (1000:1000) and Grafana (472:0) roots are created by the installer; Prometheus and the Grafana provisioning and dashboards mounts are read-only, world-readable root-owned files; AIS-catcher has no data bind mount.
- Docs and tests: README and `docs/INSTALLATION.md` troubleshooting entry; `docs/DEPLOYMENT.md` renumbered to 0.4.3. Tests cover creation before `compose up`, repair of a root-owned directory (empty and populated), refusal of symlinks, and the doctor hint.
- Fixed: **Boat Chat never became ready on a fresh install.** `/health` showed `readiness.layers.memory = {ready: false, chunks: 0}` because the memory index was only ever built by hand (`memory_index.py rebuild`); neither the installer, the telemetry-indexer timer nor `vesselstackctl` ran it. New `scripts/memory-index.sh` runs `memory_index.py` as the service user (`runuser`, or `setpriv`) with the units' minimal environment (`env -i`, `BOAT_CHAT_STATE_DIR`, `BOAT_CHAT_ENV`; `BOAT_CHAT_EMBEDDING_MODEL` and `BOAT_CHAT_MEMORY_DB` only when set in `config/boat-chat.env`, validated and never sourced) and checks that everything it created is owned by the service user. `memory_index.py` gains `ensure` (rebuild only when the index is missing, empty or the stored hash of the source documents, or the embedding backend, changed; fails when no document could be indexed) and `rebuild` now records that hash. `install.sh` runs `ensure` after the code, facts file and virtualenv are in place, on every run (so upgrades of existing installs get an index); a failure prints a `WARN` with `sudo vesselstackctl reindex` and does not abort. `vesselstackctl start` runs it before starting Boat Chat; `telemetry_indexer.py run` runs it first on every timer run (failures are recorded, never stop the telemetry refresh), so changed knowledge files refresh the index within five minutes.
- Added: `vesselstackctl reindex` (forced rebuild as the service user) and a `vesselstackctl doctor` memory-index check: FAIL with the one-line fix when the index has no chunks (read from the running service's `/health` readiness; if that does not answer, from the helper as the service user, because root must never open the SQLite file), WARN when it cannot be determined.
- Fixed: `vesselstackctl urls` was misleading. It printed SignalK and Home Assistant as `http://127.0.0.1:3000` / `:8123` (the client URLs) although those host-networked containers listen on all interfaces. It now reports the real bind of every service from `ss -ltn` (falling back to configuration, and saying so, when `ss` is missing or a published port is not visible to it, e.g. Docker without userland proxy), lists this machine's reachable addresses (`HOSTNAME.local` and each non-loopback, non-Docker/veth/bridge IPv4 address) as URLs for the services other devices can reach, and marks loopback-only services "this device only" with how to change that. MQTT is listed too.
- Fixed: a re-render of an installed system from `config/vesselstack.env` (`vesselstackctl update`, restore) reset `BOAT_CHAT_HOST` in `config/boat-chat.env` to `0.0.0.0`, silently undoing a loopback setting. The installed `vesselstack.env` has never carried that key, so the installer now keeps the installed value unless the input configuration really sets it.
- Tests: `tests/test_memory_index.py` (idempotent `ensure`, hash-driven refresh, empty index, missing documents, the readiness layer, the indexer survives a failing memory refresh); `tests/test-clean-install.sh` (index built on a fresh install, runs via `runuser -u USER -- env -i ...`, owned by a real unprivileged service user without root-owned side files, idempotent re-run, upgrade case, failure path with the WARN and a successful install); `tests/test-lifecycle.sh` (`reindex`, doctor FAIL/OK/WARN cases, `urls` with stubbed `ss`, `ip` and `hostname`: all-interface, loopback and address-specific listeners, host-networked services, ignored bridges, fallback to configuration).
- Added: **LAN access presets.** The terminal wizard asks "Who should be able to reach the dashboards?" (`local`, `dashboards` (default) or `all`) and `--set LAN_ACCESS=...` works unattended; the answer expands into `VESSELSTACK_WEB_BIND_ADDRESS`, `VESSELSTACK_DATA_BIND_ADDRESS` and `BOAT_CHAT_HOST` and is never stored. `CONTROL_PANEL_HOST` stays `127.0.0.1` in every preset. `all` warns that Prometheus has no login and recommends the firewall; an enabled firewall with an untrusted interface (default `wlan0`) is reported as blocking LAN access. Host-networked SignalK and Home Assistant cannot be restricted by these settings and the wizard and docs say so.
- Added: `vesselstackctl lan [local|dashboards|all] [--dry-run] [--yes] [--allow-firewall-conflict]`: shows the current preset (or `custom`), rewrites the keys atomically (same directory, owner and mode kept, symlinks refused, restored on failure), re-applies with `compose up -d` and a Boat Chat restart, refuses `all` without `--yes` and refuses to open the network when the firewall would block it, and warns about a Boat Chat Settings-page `BOAT_CHAT_HOST` override.
- Security: the SignalK data directory repair no longer runs a blind recursive `chown` as root. Empty directory: `chown -h` of the directory only. Populated `root:root` (the known Docker state): locked to 0700 during the change, refused if it contains symlinks, files with several hard links or special files, then chowned with a non-following same-filesystem walk and the original mode restored. Populated and owned by anyone else: no change, manual instructions printed.
- Docs and tests: README and `docs/INSTALLATION.md` section "Reaching VesselStack from other devices" (presets, `wlan0`/firewall caveat, laptop `curl` test); tests cover the preset mappings, that the Control Panel is never exposed, dry run, refusals, the firewall interplay and each repair branch (empty, populated root-owned, hard link, symlink, FIFO, foreign-owned).
- Rollback: `sudo vesselstackctl lan dashboards` restores the previous default; the repair change needs no rollback.

## 0.4.2 - 2026-10-26

- Added: headless-first installation. `scripts/get-vesselstack.sh` now asks its configuration questions **in the terminal**, so the whole install works over plain SSH (`ssh -t USER@PI`, paste the one-liner, answer the prompts) with no browser, no URL and no tunnel. The terminal wizard is `vesselstack-wizard.py --cli`. ## 0.0.1 - 2026-08-21

### Added

- Reproducible Raspberry Pi OS and Debian-family installer with generated
  credentials, pinned multi-architecture images, and systemd confinement.
- Existing, Docker, and native SignalK modes.
- Opt-in, hardware-probed SocketCAN and AIS-catcher modules.
- Configurable InfluxDB schema with idempotent bucket and downsample-task
  provisioning.
- Grafana datasource and system-health dashboard provisioning.
- Generic Home Assistant battery, bilge/high-water, and shore-power alert
  blueprints plus a Lovelace starter view.
- `vesselstackctl` status, start, stop, restart, backup, verified restore,
  guarded update, and uninstall workflows.
- Optional untrusted-interface firewall and explicit legacy-0.1-to-0.0.1 configuration
  migration.
- Clean-install, migration, recovery, ARM64 manifest, application, packaging,
  and disposable service-integration test gates.

### Safety

- Hardware and firewall modules remain disabled by default.
- Safety automations require explicit entity, threshold, duration, and action
  selection.
- VesselStack remains advisory software and is not certified navigation,
  collision-avoidance, alarm, engine-control, or life-safety equipment.
